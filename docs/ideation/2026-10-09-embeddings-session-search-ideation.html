Grounding Context

Codebase context. claude-JSONL-browser is a Next.js 15 / React 19 app that is currently fully client-side ("no data sent to servers", README.md:77). It preprocesses a Claude Code session into a sharded static index under public/sessions/<id>/ — manifest.json, search.json, turns/<n>.json, agents/<id>.json — served by fetch from BASE='/sessions', with no API routes. The reference session indexes to 290 turns, 20,209 items, 3,206 tool calls, and 1,903 subagent transcripts (main ~70 MB, subagents ~900 MB raw). Search today is a client-side String.includes linear scan over the entire search.json (9.97 MB / 21,432 docs), capped at 300 results in document order.

The embeddable unit today is a flat SearchDoc (id, kind: 'turn'|'agent', turn/item/agent, label, text) with hard truncation: searchLimit 2000, thinking 1000, tool input and result 1000 each, agent doc = description + task + finalText. The 114 MB of subagent bodies are written to agents/<id>.json but never enter the search corpus beyond a ≤2000-char summary.

External context. This niche is already crowded and converges hard: Mneme (LanceDB + nomic + FTS + cross-encoder rerank; explicitly skips tool/thinking noise), SessionFlow (EmbeddingGemma-300M + Milvus HNSW + SQLite FTS5 + RRF, with an incremental watcher), and transcript-search-v2/lore/claude-chat-search (a single SQLite file holding chunk rows + FTS5 + sqlite-vec in one transaction). The repeated lesson is hybrid-or-nothing: vector-only search is uniformly reported as disappointing. LM Studio's /v1/embeddings is OpenAI-compatible but has known sharp edges — concurrent requests hang (bug #7), usage.prompt_tokens is always 0 (#1546), it crashed under concurrency in v0.3.34, its normalization is undocumented, and its 2K context truncates silently. For a single-user app the only zero-ops stores with no separate process are sqlite-vec (single file, brute-force, KNN k=4096 cap ≈ 50–100K vectors) and LanceDB (native BM25+RRF, mmap beyond RAM). Cross-domain, observability systems teach index-everything vs label-only and time-sharding; email/legal eDiscovery teaches that the meaningful unit is the thread, not the message.

1Index the 114 MB of subagent bodies you currently discard

Embedding unit & chunkingConfidence 95%Complexity High
Description
Each of the 1,903 subagents contributes exactly one searchable doc built from its description, a 240-char task, and a 240-char final answer — the entire middle of the subagent's work is invisible to search. Emit one embeddable doc per agent item (reusing the existing SessionItem stream and the a:<agentId> jump target) and interleave the main thread and every subagent into a single timestamp-ordered, hash-deduped stream, so "the session" is literally every event that ran.
Basis
direct: lib/jsonl/session-index.ts:991 builds the agent doc as truncate([header.description, header.task, finalText]…), while scripts/build-session-index.ts:167 writes the full body to agents/<id>.json and pushes only that summary into search.json. external: chis.dev indexes two levels (session + turn); plaso/log2timeline merges many sources into one super-timeline.
Rationale
This is a coverage problem, not a latency problem — a 10 MB substring scan is already instant. The single biggest reason "search entire sessions" fails today is that ~90% of the bytes, and almost all of the reasoning, never enter the index. Fixing the unit converts the feature from "search the main thread" into "search everything Claude did".
Downsides
Corpus grows ~10× (to ~100 MB of chunk text), so embedding time, store size, and the search payload all rise; needs dedupe and per-kind filtering to avoid tool-noise drowning the signal; the existing per-session static-file model must be sized for it.

2Chunk for meaning: turn-pair, tool-pair, and agent-trajectory units

Embedding unit & chunkingConfidence 88%Complexity Medium
Description
Stop embedding items in isolation. Embed each tool call as one request↔response unit (today the input and result are truncated separately and can evict each other), each prompt↔response as a turn pair, and each subagent as a whole trajectory with its turns as children. Retrieve on the child chunk but return the parent arc (small-to-big / parent-document retrieval), keeping the existing doc id as the jump target. Route by kind: embed prose (prompt, assistant text, thinking), keep tool identity and file paths as structured filters, and content-hash artifacts so identical attachments embed once.
Basis
direct: lib/jsonl/session-index.ts:604 emits one doc per item; :314 truncate is return value.slice(0, limit) — a front slice with no overlap, so the tail of every long item is permanently unsearchable. external: lore's turn-pair chunking, chis.dev's two-level docs, and parent-document / small-to-big retrieval are the standard remedies for fragment-level hits.
Rationale
A coding session's unit of meaning is the exchange or the task, not a 2,000-char slice. Item-level vectors return fragments the user must manually re-assemble by scrolling, and the current front-slice throws away the back half of exactly the long tool outputs and thinking blocks that carry the most signal.
Downsides
More chunking logic and a parent/child id scheme to maintain; overlap increases storage; "return the parent" changes what the results list shows, which ripples into the viewer's jump and highlight behavior.

3Replace the 300-in-doc-order scan with hybrid ranked retrieval

Vector store & hybrid retrievalConfidence 90%Complexity Medium
Description
The current search returns the first 300 substring hits in document order, so the most relevant turn can sit invisible behind 300 earlier matches. Replace it with a hybrid retriever: a vector KNN leg for meaning plus a lexical leg — a trigram postings index (zoekt/livegrep-style) that finds exact identifiers such as session-index.ts or spams_s_get_vehicle_data, which tokenized BM25 splits and loses — fused with reciprocal-rank fusion, returning a ranked list with score provenance. Add a structured "find all references" leg over file paths, tool names, and PR links.
Basis
direct: components/jsonl/SessionIndexViewer.tsx:208–220 is a linear doc.text.toLowerCase().includes(needle) loop that breaks at 300 — a filter, not a ranking. external: the hybrid-or-nothing consensus across Mneme / SessionFlow / lore; zoekt and Sourcegraph build trigram and symbol indexes precisely because code-like text defeats tokenization.
Rationale
The pain is ranking as much as semantics. A substring filter cannot order results, so relevance is decided by document position. Fusing a lexical leg (exact strings developers search by name) with a vector leg (meaning) is the minimum bar the whole field has converged on, and it keeps the feature useful even before any embedder is present.
Downsides
Two retrieval paths plus fusion to tune and explain; a static trigram postings file adds a new build artifact; RRF discards score magnitude, so thresholding needs a fused-score scheme rather than a raw distance cut.

4Static doc vectors + browser-side query encoding via local LM Studio

Architecture boundary & deploymentConfidence 80%Complexity High
Description
Split the work by time. At index time the Node CLI — where LM Studio is local — precomputes every doc vector and ships them as a static, sharded binary sidecar next to search.json; at query time the browser encodes only the query and runs a brute-force cosine pass fused with the lexical leg, degrading silently to lexical-only when no embedder is reachable. Stamp the artifact with an embedding contract (model, dims, normalized, available) so a model or normalization change is detected rather than silently corrupting similarity.
Basis
direct: README.md:77 "Client-side processing (no data sent to servers)" coexists with README.md:7's public live demo, and AGENTS.md:53 forbids API routes; SESSION_INDEX_VERSION=1 and the payload version show the artifact-versioning convention. external: LM Studio's /v1/embeddings is OpenAI-compatible and local; EmbeddingGemma supports Matryoshka truncation; its normalization is undocumented and its 2K context truncates silently.
Rationale
Query embedding is the only runtime model dependency. Precomputing docs and shrinking the runtime model to the browser keeps the serverless, privacy-preserving boundary intact while still delivering true semantic recall, and the same static build degrades gracefully on the hosted demo that has no LM Studio.
Downsides
A browser-side embedding model (EmbeddingGemma-300M-class via transformers.js/WebGPU) is a heavy new client dependency and may not run on all devices; brute-force cosine in the browser does not scale past a few hundred thousand vectors; the whole approach hinges on an unverified normalization/truncation contract that must be tested empirically.

5Content-addressed embedding cache → incremental re-embed and a session watcher

Ingest pipeline & freshnessConfidence 92%Complexity Medium
Description
Every rebuild currently deletes the output directory and re-derives everything, so embedding would be redone in full on each run — fatal given LM Studio's concurrency hangs. Add a persistent cache keyed by sha(text + model + dims + version) so unchanged docs skip embedding and only new or changed turns and agents are sent, driven through a single-worker queue with modest batches and responses sorted by index. Because the cache makes delta runs cheap, a long-running watcher can then embed only the appended JSONL tail and remove the manual npm run index ritual.
Basis
direct: scripts/build-session-index.ts:142 if (existsSync(outDir)) rmSync(outDir, { recursive: true, force: true }) — a full teardown every run; builtAt is wall-clock, not content-derived. external: git's content-addressed object store and Bazel/Salsa red-green recomputation; SessionFlow ships an incremental watcher over 21K+ turns; LM Studio hangs/crashes under concurrency.
Rationale
Embedding cost is intrinsically O(changed docs), not O(corpus). A hash-keyed cache converts the expensive first build into a one-time investment and turns every later re-index nearly free — and it minimizes exactly the LM Studio calls that destabilize the embedder. It is the precondition for both a watcher and any multi-session scale-out.
Downsides
A new persistent, gitignored cache directory to manage and invalidate; correctness depends on hashing the exact embedded text (normalization and truncation included) so a silent model change does not reuse stale vectors; the watcher adds a local-only daemon that the static-host model cannot assume.

6Explainable, filterable semantic results

Query & UX in the viewerConfidence 85%Complexity Medium
Description
A semantic hit has no literal match, so the existing snippet helper falls back to the first 200 characters and the user cannot see why a result is relevant. Store the matched chunk span per result and render that span with its surrounding item, plus a "why this matched" cue naming the source index (reasoning / change / context) and the fused score. Add filter chips over metadata already in the headers — kind, tool name, subagent type, model, error, time range — so a query can be scoped before it runs, and pre-filter the candidate set before KNN.
Basis
direct: SessionIndexViewer.tsx:576–582 — snippet() returns text.slice(0, 200) when indexOf is −1, which is the normal path for a vector hit, and Highlight wraps literal matches only; the agent-list filter at :222–233 already matches description/subagentType/model/task/id, and TurnHeader/AgentHeader carry the facets. external: observability's rule that high-cardinality fields belong in structured metadata, not labels; rerankers surface scores users need to trust.
Rationale
Semantic search only pays off if the user can confirm relevance at a glance and narrow scope. Without matched-span evidence and filters, the feature will feel worse than substring search for the queries that do match literally — the exact trust failure that kills adoption.
Downsides
Requires storing chunk spans and scores in the payload; adds query-UI surface (facet chips, score display) and a candidate pre-filter path; explaining a fused score honestly without implying false precision is a design problem, not just a rendering one.

7Cross-session "I solved this before" search

Query & UX in the viewerConfidence 82%Complexity High
Description
Search is strictly per-session today — the catalog lists sessions but carries no doc text — so a user who remembers fixing a problem in some earlier session has no way to find it. Build a catalog-level embedding index keyed by session id and turn the session picker into a scope toggle ("this session" / "all sessions"), returning the session plus the matching turn as the result. Keep the per-session payload intact so opening a result still loads only one shard or agent transcript.
Basis
direct: SessionIndexViewer.tsx:123–132 ensureSearch loads only fetchSearch(sessionId); scripts/build-session-index.ts:215–229 writes the catalog with only id/title/counts/models/bytes and no doc text. external: email/legal discovery indexes the thread unit and metadata separately; observability time-shards an index-everything corpus.
Rationale
The recurring real-world query for a returning user is "where did I do this before", which is cross-session by nature and impossible in the current single-session scan. It turns the session catalog from a file list into actual memory — the highest-value retrieval question the tool currently cannot answer at all.
Downsides
A second, catalog-level index to build and keep fresh across sessions; much larger corpus (many sessions × 20K docs) pushes past brute-force comfort and re-raises the store question; result UX must convey session context, and stale sessions need re-indexing discipline.
