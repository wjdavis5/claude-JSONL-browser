Grounding Context

Codebase context. claude-JSONL-browser is a fully client-side Next.js 15 app that preprocesses a Claude Code session into a static index (manifest.json, search.json, turns/<n>.json, agents/<id>.json) served from public/sessions/ with no API routes. The reference session is 290 turns, 20,209 items, 3,206 tool calls, 1,903 subagents; search.json is 9.97 MB / 21,432 docs and the 114 MB of subagent bodies never enter search beyond a ≤2000-char summary. Search is a client-side includes scan capped at 300 in document order.

What a graph can be built from today. Nodes: session, turn, item (9 kinds), agent, tool, tool-call↔result pair, PR, file, background task. Edges already derivable: agent→parent (AgentLink.parentId), item→agentId, tool_use↔tool_result by tool_use_id, turn→item, session→agent/PR, catalog→session. Gaps: file paths live only in result-side toolUseResult.filePath (input file_path is stored but never keyed), structuredPatch bodies are dropped to a line count, the uuid/parentUuid message DAG is never read, SendMessage is unrecognized, and the catalog has no shared key for cross-session joins.

External context. The store question has a proven answer: FTS5 + sqlite-vec + graph tables coexist in one SQLite file, sharing rowid and fusing lexical and vector hits with RRF in a single CTE. sqlite-vec is brute-force (~250k vectors under 100 ms; 1M fails; default KNN k cap 4096). Graph-in-SQLite is nodes+edges plus WITH RECURSIVE (~100K–1M node ceiling). Dedicated embedded graph engines are a trap — Kùzu was archived in Oct 2025 and acquired by Apple; Oxigraph is a RocksDB directory with SPARQL and no vectors; Neo4j embedded is JVM-only; Memgraph is a daemon. Agent-trace graph prior art is active: AgentGraph (AAAI 2026, SQLite-backed, PROV-O-like), GRADE (execution vs dependency edges, each graded observed/declared/inferred), AgentTrails (a joined quotient graph that aligns multiple traces for cross-session and duplicate-work detection), and Graphiti/Zep (bi-temporal episodes→entities→community). Closest shipping competitors already run this stack: kmizzi/claude-code-sessions (Next.js + better-sqlite3 + FTS5 + sqlite-vec, no graph), cc-search, and knowledge-graph-rag-mcp (EmbeddingGemma + sqlite-vec + BFS). Cross-domain vocabulary worth borrowing: W3C PROV-O, data lineage, the Git commit DAG, and SBOM PageRank.

1One SQLite, one identity: full text, FTS5, vectors, and graph share a single rowid

One-file schema & storageConfidence 92%Complexity High
Description
Make one SQLite file the source of truth. Every item, agent, turn, file, and session gets a single INTEGER primary key; the FTS5 table, the sqlite-vec vec0 table, and the graph's nodes/edges tables all reference that same rowid, so hybrid retrieval is JOIN … USING(rowid) with RRF computed in one CTE. Store the full untruncated text (including the 114 MB of subagent bodies) and treat today's search.json/manifest.json as render-time exports. The graph is canonical; text and vectors are projections over it, with bi-temporal validity (t_valid/t_invalid) so "as of turn N" is a WHERE clause.
Basis
direct: lib/jsonl/session-index.ts:314 truncate is return value.slice(0, limit) and :660 searchLimit ?? 2000, so search can never match text that was sliced away; ids are two disjoint string keys, t<turn>:<item> (:654) and a:<agentId> (:992); scripts/build-session-index.ts:201 writes one flat search.json. external: FTS5 + sqlite-vec sharing rowid with RRF in one CTE is a documented, author-confirmed pattern; Graphiti/Zep's bi-temporal model.
Rationale
Three parallel key spaces and three stores is exactly how hybrid search drifts out of sync, and the current front-slice means the feature cannot retrieve what it threw away at build time. One rowid makes vector, keyword, and graph results trivially joinable and removes a whole class of "which id did this doc have" bugs — it is the foundation every other idea compounds on.
Downsides
SQLite becomes a required runtime dependency, which conflicts with the repo's "no API routes / no server" identity (see idea 6 and the noted alternatives); full untruncated text + vectors push the artifact toward ~100 MB per session; browser access needs WASM SQLite or a local sidecar; sqlite-vec's brute-force ceiling bounds multi-session scale.

2Content-addressed incremental ingest with snapshots

One-file schema & storageConfidence 90%Complexity Medium
Description
Key every node by a content hash and upsert into SQLite instead of deleting the output directory. A snapshot row per npm run index run, plus manifest rows enumerating which turn/agent/doc rows belong to it, gives metadata-only supersede and "as of any build" queries; re-indexing a growing session writes only new turns and re-embeds only changed items. Replace the wall-clock builtAt with a content hash so the viewer can tell what is actually stale.
Basis
direct: scripts/build-session-index.ts:142 if (existsSync(outDir)) rmSync(outDir, { recursive: true, force: true }) — a full teardown every run; :61 readJsonl loads and parses whole files; lib/jsonl/session-index.ts:878 stamps wall-clock builtAt. external: Git's content-addressed object store, Bazel red-green incremental builds, and the Iceberg/Delta snapshot + manifest model for metadata-only operations.
Rationale
Re-embedding 21k docs plus 1,903 agent bodies per run is the dominant cost and forces a full reload; content-addressed upsert turns minutes into seconds and is the precondition for both a live-append watcher and multi-session scale-out. Iteration speed on the corpus is the compounding asset here.
Downsides
A persistent, gitignored cache/database to manage and invalidate; correctness depends on hashing the exact embedded text (normalization and truncation included) so a silent model change does not reuse stale vectors; snapshot bookkeeping adds schema surface.

3Rebuild the true execution DAG — and repair compaction

Session graph modelConfidence 88%Complexity Medium
Description
Preserve the raw uuid/parentUuid message chain and SendMessage as first-class edges, so the subagent structure becomes a real execution DAG with fan-in and fan-out instead of a tree. Grade each edge observed / declared / inferred so retrieval can weight them and the viewer can show "this agent's result fed four others". Because compaction drops the pre-compaction region — leaving orphaned tool results as standalone items — build the graph from the uuid chain first (the true message tree), then linearize for display, so compaction gaps and rewinds become edges instead of losses.
Basis
direct: rg parentUuid returns nothing repo-wide — session-index.ts reads neither uuid nor parentUuid; MAIN_AGENT_TOOLS = new Set(['Agent','Task']) (:213) misses SendMessage; orphaned tool results are handled at :491; backgroundTaskId/taskId are kept only as scalars (:355). external: PROV-O's wasInformedBy, the Git commit DAG, and GRADE's graded execution/dependency edges.
Rationale
The tree lies about async and background work, and compaction silently rewrites history — the two most disorienting failures in long agentic sessions. A graded DAG reveals cross-agent dependencies the viewer cannot show today, restores turn ancestry across compaction, and gives ranking a principled confidence signal.
Downsides
Requires reading raw records the pipeline currently ignores (more parser surface and memory during ingest); inferred edges can be wrong and must be labelled as such; a DAG complicates the linear "turn list" the viewer is built around.

4Cross-session graph on shared keys — sessions become subgraphs

Session graph modelConfidence 85%Complexity High
Description
Promote file paths (parsed from tool inputs, not just toolUseResult.filePath), tool names, PR numbers, gitBranch, cwd, and content hashes to canonical nodes shared across sessions, then build one union graph in which a session is a subgraph. Type the cross-session edges by temporal direction — affirms, supersedes, distinguishes — so browsing old work reveals what is still good ("superseded by session B, turn 42"). Borrow FRBR-style authority records so one file is a single entity linked from every session that touched it.
Basis
direct: the catalog (lib/jsonl/session-index.ts:169–178) stores only id/title/counts/models/timestamps — no shared identifier — and ensureSearch loads a single session (SessionIndexViewer.tsx:123–132). external: AgentTrails' joined quotient graph aligns traces across executions for cross-session and duplicate-work detection; FRBR authority control and legal citators (Shepard's/KeyCite) for typed supersession.
Rationale
The user's explicit goal is edges between sessions, and the highest-value question — "have I done this before?" — is structurally unanswerable when the session is the root node and there is no shared key. Once keyed, "same file in 7 sessions", "same PR", and "recurring error" become plain joins, and value grows with the corpus rather than per session.
Downsides
A much larger corpus across many sessions pushes past brute-force comfort and re-raises the ANN question; entity resolution (is this the same file/branch?) needs normalization rules; stale sessions need re-indexing discipline; the citator semantics add modeling complexity.

5Tool→file change lineage from inputs and patch hunks

Graph & edge extraction at ingestConfidence 88%Complexity Medium
Description
Parse file_path out of Read/Edit/Write inputs (stored verbatim but never keyed) and retain the structuredPatch hunks that are currently collapsed to a line count, emitting typed tool→file edges tagged by operation (read / edit / write) plus file co-change edges. The result is PROV-O-style change lineage: which agent changed line X of a file, in which turn, verified by which test run — and, chained, Read→Edit sequences and "files this session owns".
Basis
direct: only result-side toolUseResult.filePath is kept (lib/jsonl/session-index.ts:344); structuredPatch becomes meta.patchLines = tur.structuredPatch.length (:371); input.file_path is stored raw (:418) but never keyed. external: data-lineage / PROV-O graphs, compiler SSA def-use chains (tool_use↔tool_result is already a def-use pairing at :456), and SBOM co-change graphs.
Rationale
File identity is the join key connecting tools, agents, and sessions — the highest-yield missing edge in the current model. Without it the graph is only agent→parent and cannot support impact analysis or cross-session retrieval, and it costs nothing extra because the data is already in memory during the build.
Downsides
Tool input shapes vary (MCP tools, Bash heredocs, notebooks), so path extraction needs a per-tool strategy and will be incomplete; retaining patch bodies grows the database; "same file" comparisons need path normalization (absolute vs repo-relative, worktrees).

6Graph-expanded hybrid retrieval — FTS5 + vectors + graph in one ranked pass

Graph + hybrid retrievalConfidence 90%Complexity Medium
Description
Replace the linear includes scan (capped 300, document order) with a two-stage query: FTS5 and sqlite-vec candidates fused by RRF, then one-hop expansion along the graph (tool_use↔result, agent→parent subtree, file co-change) with a Personalized-PageRank rerank seeded from the matched nodes. Because text, vectors, and graph share rowid, each future signal is a new leg in the same CTE. Optionally materialize the neighbor lists and centrality at ingest so the browser renders neighbors instantly from a static file, with no query-time traversal.
Basis
direct: the entire retriever is the loop at components/jsonl/SessionIndexViewer.tsx:208–220 — a linear includes that breaks at 300, with no ranking. external: single-CTE RRF over FTS5 + sqlite-vec; Personalized PageRank (Haveliwala 2002) and SBOM-style PageRank; GraphRAG local/global hybrid retrieval; transitive-closure materialization for low-latency client lookup.
Rationale
Substring order buries the best hit behind the 300th and returns no context. Graph-expanded hybrid retrieval surfaces the causally-relevant turn even when the query words never appear in it, and returns the story around a hit — its tool result, sibling agents, touched files — so the graph investment pays off at query time rather than only at ingest.
Downsides
Two-plus retrieval legs and a fusion/rerank scheme to tune and explain; RRF discards score magnitude so thresholding needs a fused-score design; graph expansion can amplify a bad seed (needs a relevance floor); precomputed closure adds build cost and artifact size.

7Graph as navigation: provenance on every block, a neighborhood lens, and a duplicate-work rail

Query & UX in the viewerConfidence 82%Complexity High
Description
Today only search results carry links into the session; every other block is a dead end. Invert the arrow: every rendered block (tool call, agent, attachment) exposes outbound provenance — its matched result pair, the file it touched, sibling agents on the same file, and other sessions touching that file — and a persistent neighborhood panel updates as you navigate, so text/vector search becomes one affordance inside a live graph lens rather than the only entry point. Surface a duplicate-work rail built from an AgentTrails-style quotient graph, and let the lens rank "hot spots" by graph centrality.
Basis
direct: jumpToResult maps a doc to a turn/agent view only (SessionIndexViewer.tsx:235–245) and SessionBlocks renders blocks with no outbound edges; SessionItem.isError (session-index.ts:47), compaction items (:621), and AgentHeader.status (:89) are available to mark anomalies. external: AgentTrails' quotient graph for duplicate-work detection; Graphiti/Zep community summaries as a navigation concept.
Rationale
Exploration is how you actually debug a long agent session, and the current UI forces you to leave what you are reading and guess a keyword. Making the graph the navigation surface removes the "I must know the word" tax, exposes cross-session and file relations the flat list cannot show, and turns every new edge type into a navigable affordance for free.
Downsides
A graph explorer is a large UI build on top of an already-dense viewer; neighborhood panels can overwhelm and need curation; duplicate-work detection produces false positives that erode trust; ranking by centrality can surface noise if the graph is sparse.
